# 评审 0004：系统整体设计复核

- 日期：2026-11-10
- 性质：**设计期收官后的独立复核**——对设计 0001~0006/0008、ADR-0001~0006、规则库实物（8 个 YAML）、代码（models/loader/CLI）做三方交叉核对
- 方法：文档 ↔ 文档、文档 ↔ 实物、实物 ↔ 实物、文档 ↔ 代码四向比对；重点找**不一致与缺口**，不复述设计内容
- 范围外：规则**内容**的正确性（阈值是否与现行法规一致——属校准 #5，文档自述 `calibration_pending`）；UI 视觉（用户自评已过）
- 结论：**架构骨架成立、可进入实现**，但有 1 个 P0 公式错误必须在实现前修正，另有 4 处跨文档不一致需收敛（详见 §2）

## 0. 总评

| 维度 | 评价 |
|---|---|
| **架构完整性** | ✅ 成立。三域八模块 + 五节点责任链 + 单向数据流构成闭环，模块边界与权限（谁能写规则库）已明确 |
| **语义单点性** | ✅ 成立（这是本设计最大的优点）。窗口/缺数/量词/折叠各有唯一定义点，G-B 的教训已被结构性吸收 |
| **跨文档一致性** | ⚠️ **有缺口**——P0×1 + P1×4：设计之间的数值/形态/口径未完全收敛（§2） |
| **实物对齐度** | ⚠️ 规则库仅铺 2/43 组（已知，属实现期）；但 `_meta` 形态与设计示例**不一致**（V2） |
| **可实现性** | ✅ 每条决策都能落到具体文件与断言；lint L1~L6 已实现并有 12 测试守护 |

## 1. 做对的地方（值得固化，不建议在实现期改动）

1. **勘误机制**：评审 0003 v2 主动撤回「98 分掩盖一票否决」的论断（459a1b9）；0001 §2.3 加勘误注（Kleene 双规则）；0001 加勘误注二（附录 A 数值矛盾）；ADR-0002 加 R2 勘误注——**设计文档能被自己的文档推翻，是可信度来源**。
2. **权威源链单向**（原文 → YAML → 快照仅 trace）+「证人不是法官」（L3 快照只作佐证，不一致必人工看）——避免了「校准退化成原样抄库」。
3. **五态 + null 永不进比较**：直接对应 midas `ResultEvalServiceImpl:149` 的病灶，是可验证的修复而非理念宣示。
4. **lint L1~L6 = 校准 L0 的运行时形态**：同源规则写两遍（设计 0003 §3 与设计 0002 §4），并做**双向编号消歧**（两个文档都加了对照注）——这在多文档项目里极易出错，处理得当。
5. **甲公司贯穿算例**：从 0001 附录 A 一路贯穿到 0004 走查、0005 自检链、0006 定稿表、0007 UI——跨文档验算有了共同锚点，这是本项目最有效的防漂移手段。

## 2. P0：实现前必须修正（1 项）

### V1 · 设计 0005 §4.2 的 CAGR 公式方向颠倒，且与同文 §6 自相矛盾

**证据**（`docs/design/0005-engine-runtime-and-formula-semantics.md`）：

- §4.2 量词公式表写：`cagr | v = (x[首年]/x[末年])^(1/(n−1)) − 1`
- §6 window_roll 表写：`cagr | 首年′ × (1+thr)^(n−1)`

两式互推：**若 CAGR 真按 §4.2 定义（末年是分母），则 §6 的进入年所需值公式应是 `末年′ ÷ (1+thr)^(n−1)`，而不是乘法。** 两式必有一错，而 §6 的乘法式与「复合增长率」的标准定义一致 → **§4.2 是错的**。

**白话 + 算例**（甲公司，2022 营收 4.2 亿 / 2024 营收 6.8 亿，窗口 n=3）：
- 正确：`(6.8/4.2)^(1/2) − 1 = 27.3%`（三年营收复合增长率，应为正）
- §4.2 字面：`(4.2/6.8)^(1/2) − 1 = −21.4%`（**符号与量级都反**）

**影响面**：`rev_1y_growth`（1 年增长率）、`rev_3y_cagr`、`rd_3y_cagr` 三个 item 全走此量词；创业板第四套「增速≥30%」这一法定指标直接依赖它；ADR-0006 第 4 条引用该表，实现者照抄即错。

**建议**：改为 `v = (x[末年]/x[首年])^(1/(n−1)) − 1`，并在 §4.2 下方加一行交叉引用（§6 的 window_roll cagr 式为该式的反解），同时在 ADR-0006 补勘误注。**这是实现前唯一的阻断项。**

## 3. P1：跨文档不一致，需收敛（4 项）

### V2 · `_meta.yaml` 的 `declared_no_sets` 形态：设计示例与实物/代码不兼容

- 设计 0002 §2.1 示例把豁免写成 per-combo 布尔；实物 `rulebook/_meta.yaml` 与 `models.py: Meta` 用的是**全局列表** `declared_no_sets: [[BSE, redchip_unlisted], ...]`。
- 照设计 §2.1 写出的 YAML **装不进现有 loader**（`Meta.declared_no_sets` 是 `list[list[str]]`，喂 `[{board:…, company_type:…}]` 直接校验失败）。
- **建议**：设计 0002 §2.1 的示例更新为实物形态（并补一句「L2 豁免在 `_meta` 全局声明，不逐组合散写」），避免后续校准照设计写数据时踩坑。

### V3 · 甲公司逐年数值分叉：设计 0006 定稿 vs 设计 0007 UI mock

| 年 | 0006 §5（定稿） | 0007 §4（UI mock） |
|---|---|---|
| 2023 营收 | 50,000 万 = **5.0 亿** | **5.3 亿** |
| 2024 营收 | 68,000 万 = **6.8 亿** | **6.5 亿** |

- 累计均为 16.0 亿 → **累计型判定（营收 3 年累计 ≥15 亿）结论一致**，但**逐年增长率与窗口滚动结果不同**：定稿 (6.8/5.0−1)=+36%，UI (6.5/5.3−1)=+22.6%。
- 更要紧的是 0007 §4 另有一处 `window_roll` 数字「营收支路需 ≥3.5 亿 vs 6.5 亿」——按定稿应为 vs **6.8 亿**。
- **建议**：以 0006 §5 为唯一来源（它有逐年勾稽①②③且已平衡），0007 §4 的 mock 段加一句「数值取自设计 0006 §5 定稿表」，并把 5.3/6.5 改为 5.0/6.8、window_roll 的 6.5 改为 6.8。

### V4 · 设计 0007 以 DB 快照为规则源，与 AR1「YAML 唯一权威源」冲突

- 设计 0007 §4：「套结构 = DB 快照（`mt_ipo_listing_standard` 沪主板·一般企业 sort1~4 → 官方 3 套）」；「第二套市值门槛 50 亿为 calibration 勘误修正值（快照 350 亿系笔误）」。
- 即 **UI 里的阈值不是来自 `rulebook/`，而是快照 + 人工勘误修正** → UI 事实上存在一份**影子规则库**，与 AR1（运行侧只读 `rulebook/`，快照仅 trace）正面冲突；也违背 D4 的权威源链（快照是转写件，本身有实锤笔误）。
- 叠加问题：`rulebook/` 当前只有 2 个样板组，UI 需要的 3 套（主板第一/二/三套）**在规则库里尚不存在**——原型先于数据落地，可接受，但必须显式标注「影子来源 + 待规则库落库替换」。
- **建议**：设计 0007 §4 改写为「套结构取自设计 0006 §5 与 `rulebook/sets/`（当前仅 cn_main_general_g1 已落库；第二/三套待 M1 校准管线产出）；原型内的 350→50 勘误**仅作 UI 演示标注**（已校准事实），其权威副本在 calibration/0001 §3-1 与未来的 rulebook 中」——即把「影子规则库」降级为「明确标注的演示数据」，不与 AR1 争权威。

### V5 · 归因维度枚举：设计 0007「2×2」 vs 设计 0005 §7.2 的 5×3

- 0005 §7.2 定义 verifiability 5 值（verified / missing_data / pending_worksheet / pending_judgment / pending_audit）× substantive_obstacle 3 值（none / numeric_gap / boolean_gap）= 15 组合。
- 0007 §2 写「层③归因 2×2」、§4 写「真实缺口/可补/需外部证据三类落格」——**两处都与 5×3 不符**。
- **建议**：0007 §2 改为「归因正交表（5×3，落到有值的格）」，§4 的「三类落格」改为列举具体实例（如「缺 2022 年数据」= missing_data × none、「净利差 0.6 亿」= verified × numeric_gap）——实例反而更能验证契约。

## 4. P2：覆盖缺口，须显式登记（4 项）

### V6 · `as_of_date` 生效区间过滤未实现，而三处设计都依赖它

- 设计 0004 §3「按 `as_of_date` × `effective_from` 过滤 → 结果回写 `applied_rule_versions[]`」、设计 0005 §1「规则加载（as_of 过滤）」、0001 §1.1（C5）。
- 现状：`loader.load_rulebook(root, strict_global=False)` **无 as_of 参数**，只有 `strict_global`；`effective_from` 在 `Group`/`Law` 模型里是必填字段但**从不参与过滤**。
- **建议**：登记为实现期条目（M4/M5 第一步），并明确一个语义——`effective_from > as_of` 的 group 是**排除**还是**报错**（推荐：排除 + 记入 `applied_rule_versions` 的「未生效」清单，不报错，因为规则库常含未来版本）。

### V7 · 「增长率高于同行」条件型无对应 item（条件型宇宙缺一项）

- calibration/0001 §2：红筹未上市 100 亿档的三支路之一是「**高于同行**」；0001 §3.4 把它定义为**基准库前置依赖**（未建库前一律 indeterminate）。
- 但 `rulebook/items.yaml` 26 个 item 中**没有**这一项（3 个 judgment = check32/33/34；`redchip_special`（check34）覆盖的是「研发阶段红筹/国家创新驱动」）。`check07`（同行 CAGR）在 alias 表中**无任何 item 挂载**。
- 后果：段③红筹专套铺开时（实现期步骤 4）会缺 item；且「24 条文条件型」宇宙实际是 **24 + 1（同行比）**。
- **建议**：在 items.yaml 补一个 `peer_growth_outperformance`（nature: judgment / basis: declared，pending_evidence = [可比公司集合确定方法, 同行业基准值]），或明确登记为「基准库未建前的占位 item，v1 铺开到红筹套时必补」。

### V8 · 法规原文库（`source_texts/`）不存在，M1 的输入端是空的

- 设计 0004 §3/§7 把 M1 的输入列为「原文库（法规原文 + 版本元数据）」，0003 §2 的管线从「原文库」起步；但仓库内 `raw/` 只有需求 docx 与 Excel 底稿，**没有任何法规原文条文**。
- 工作量性质：185 条文 × (文档名/版本/生效日/条款号/正文)，且必须是**现行版**（L0-8 版本对齐闸门要求），人工采集与版本核验是校准 #5 的主体工作——设计 0008 的实现期清单（A6 顺序）**未估这一块**，M1 被排在第三位，容易被低估。
- **建议**：把「原文库采集与版本台账」显式列为 M1 的**前置子项**，并注明其产出物（`source_texts/` + 版本对照表）是 L0-8 闸门的输入；在 M1 启动前先做**一个板块的原文样板**（如科创板 2.1.2 条文族）验证采集格式与版本口径，再铺全量。

### V9 · 勾稽② 的起算口径未定义（间接法调节表）

- 0006 §4 勾稽②：`np + adjustments == ocf（逐年）`，而 §2.2 的 `reconciliation.np` 取的是**归母**净利。
- 严格意义上间接法调节表从**净利润（含少数股东损益）**起算；用归母净利起算时，少数股东损益须由 `adjustments` 吸收，但 `adjustments` 的语义在文档中未定义（§2.2 也未给「净利润总额」字段）。
- **建议**：0006 §2.2 增 `net_profit_total`（净利润总额）字段，勾稽② 断言改为 `net_profit_total + adjustments == ocf`，`adjustments` 注明「含少数股东损益、折旧摊销等调节项」；这样 §4 的断言才与会计准则口径一致，也让「归母 vs 合并」的口径差在数据层显性化。

## 6. 复核结论与建议处置

**结论**：设计**批准进入实现期**，条件是 V1（CAGR 公式）先行修正——它是唯一会造成**结论反向**的错误，且已被 ADR-0006 引用，拖到实现期会被原样复制进代码。

**建议处置顺序**：

1. **立即（实现前）**：V1 修正 + ADR-0006 勘误注（阻断级）。
2. **实现期第一步（M3）**：V2（`_meta` 形态对齐，否则校准照设计写数据会失败）、V3（数值收敛到 0006 定稿，UI 同步）、V9+V10+V11（0006 字段与断言补齐——M3 就是干这个的）。
3. **实现期第二步（M4/M5）**：V6（as_of 过滤进 loader + 生效过滤语义）、V7（同行比 item）。
4. **实现期第三步（M1）**：V8（原文库采集前置项，样板先行）。
5. **随手（文档维护）**：V4、V5、V12~V17。

**复核未覆盖**：规则**阈值内容**是否与现行法规一致（属校准 #5，3 个法条文件仍 `calibration_pending`）；引擎实现正确性（尚未实现）；midas 侧存量数据治理（V8 的下游）。
